# 清空工作区数据设计

## 目标

提供一个明确、安全的“清空工作区数据”入口，用于移除测试任务、测试项目和测试里程碑，使软件回到真正的空白工作区。

## 清除范围

确认后永久删除：

- 全部任务，包括活动任务和回收站任务；
- 全部项目，包括活动项目和回收站项目；
- 全部季度目标/里程碑，包括活动记录和回收站记录；
- 当前仍可见的撤销删除状态。

清空后工作区文档仍保留合法的版本号和空数组，应用不得重新生成演示数据。

## 保留范围

不得删除或重置：

- MiniMax API Key 和凭据存储；
- MiniMax 区域、模型选择和 AI 设置；
- 界面缩放及其他 UI 偏好；
- 软件更新设置；
- 应用本身及 SQLite 数据库文件。

## 交互设计

入口位于“我的工作台”信息窗口底部的“危险操作”区域，按钮名称为“清空工作区数据”。

点击后打开二次确认对话框，显示即将删除的任务、项目和里程碑数量。用户必须在输入框中完整输入“清空数据”，确认按钮才可用。对话框明确提示此操作无法撤销。

成功后关闭对话框、刷新工作区并显示空白状态。失败时保留原数据并展示错误，不关闭确认对话框。

## 数据与接口

在 `WorkspaceGateway` 增加 `clearWorkspaceData(): Promise<void>`：

- LocalStorage：一次写入空的合法工作区文档；
- 桌面 SQLite：沿用现有串行写入和事务回滚机制保存空文档；
- Supabase：通过 owner-scoped、单事务 RPC 按外键安全顺序删除任务、季度目标和项目；
- Nuxt API：增加受现有服务端配置保护的 DELETE 路由。

“清空回收站”继续只删除软删除记录，与“清空工作区数据”保持独立语义。

## 安全与错误处理

- 不提供跳过文本确认的快捷方式；
- 执行中禁用关闭和重复提交；
- 本机/SQLite 写入失败必须回滚，不能留下半清空状态；
- Supabase 删除必须限定固定 owner ID，并在单个数据库事务中执行；
- 不触碰凭据、环境变量或项目外文件。

## 验证

测试必须覆盖：

- 本机数据清空后所有业务集合为空且不会重新播种演示数据；
- API 和 Supabase 调用使用正确的受限入口；
- SQLite 保存失败时工作区保持原状；
- 未输入“清空数据”时确认按钮不可用；
- 完成清空后任务、项目、里程碑和回收站计数均为零；
- MiniMax 和 UI 偏好存储未被修改。

本轮只运行开发预览及自动化测试，不生成或安装新安装包。
